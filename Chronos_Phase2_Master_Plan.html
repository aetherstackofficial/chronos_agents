00 Why Chronos Can Be a Startup — The USP & the Buyers

Every backtesting tool on the market shares one fatal lie: it replays a frozen historical tape and assumes your trades had no effect on it. You "buy 500,000 shares" at the historical close and the tape rolls on as if you were never there. This is the price-taker fallacy. For a retail trader moving 100 shares it's harmless. For an institution, a market-maker, or a quant fund deploying size, it's catastrophically wrong — their own orders move price, consume the book, widen spreads, and trigger other algos. Classic backtests therefore systematically overstate the profitability of any strategy that trades in size. The bigger the capital, the bigger the lie.

The one-sentence pitch. Chronos is a counterfactual market simulator: it answers the question no historical backtester can — "If I had actually traded this size, how would the market have reacted, and would my edge survive my own footprint?" We replace the frozen tape with a living, reactive limit-order-book populated by AI agents. When your order enters, it matches against real resting liquidity, moves the mid-price, and the agent population re-prices on the next tick. The backtest stops being "what happened" and becomes "what would have happened, with you in it."

Our differentiator: price-maker simulation, not price-taker replay

Agent-based reactivity

A populated, regime-aware order book that re-prices in response to your flow. The realism is an emergent property of trained agents — a data-and-tuning moat, not a feature flag a competitor can copy in a weekend.

RL-trained participants

Market-makers and whales whose behaviour is learned from market dynamics (inventory risk, order-flow toxicity, trend) rather than scripted. Harder to replicate than a rules engine, and it improves with more training data.

LLM macro-shock layer

"What if this headline broke?" — a risk desk types a scenario in English and watches the book gap. A uniquely demo-able, board-friendly capability powered by Gemini.

Scenario / war-gaming

Replay a real day, then inject a whale or a news shock and measure how your strategy and the market co-evolve. Execution research + risk + training in one sandbox.

Synthetic-data engine

A calibrated twin can generate unlimited, labelled, regime-tagged microstructure data for training other models — a second product hiding inside the first.

Impact / capacity analysis

"How much can this strategy hold before it eats its own edge?" — the single most valuable number for any fund scaling a strategy, and one no mainstream tool produces.

01 Phase 1 Recap — What We Built & How

What it does not yet deliver is the promise — because price is still a random walk, the system is single-node, and most of the AI is bypassed at runtime. Below is the architecture as actually built.

Everything speaks ZeroMQ REQ/REP ("Notice Board" / pull architecture) over TCP on ports 5555 (engine) and 5557 (oracle). The engine is a single-threaded zmq.Poller loop with a 50 ms timeout; once per second it runs "market-regime physics." The swarm is a single asyncio loop sharing one REQ socket — so despite the language of concurrency, agent actions are processed strictly one at a time.

02 File-by-File — What Each File Does & How

2.1 · Matching-Engine Layer

true_engine.py · 344 LOC · CORE — the heart

What. A native-Python, dictionary-based limit-order-book bound to a ZeroMQ REP socket on :5555 — the single source of market truth.

How. The MatchingEngine class holds two dicts, bids and asks, each mapping a rounded price → FIFO list of {agent_id, qty}, plus an agent_ledger tracking every participant's cash & position. Key methods:

  • add_order() — inserts LIMIT orders into the book.
  • process_market_order() — walks the opposite side in price-time priority, fills greedily, debits/credits both taker and maker ledgers, records each print to a 50-deep trade tape, removes exhausted levels. This is real matching logic — the strongest part of the engine.
  • calculate_rsi() — a genuine 14-period RSI over a rolling price_history.
  • apply_market_regime_physics() — runs once/second: advances a "master clock" (375 min/day, then jumps to 09:15 next day), computes a U-shaped intraday volume multiplier, flips a BULL/BEAR/RANGING regime on a timer, fires "GHOST" trades to manufacture trends and bounce price off $5 levels, prunes stale orders >$0.50 from mid.
  • generate_lob_state() — aggregates top-5 levels each side, builds the PnL leaderboard, returns the big JSON payload the UI consumes.
⚠ The fatal flaw lives here. Inside generate_lob_state() the engine runs price_drift = random.gauss(0, 0.02)*scale + regime_drift and adds it to current_price on every single FETCH_STATE. Because the UI and swarm fetch state far more often than trades land, this random walk dominates the visible price — the order book is in practice mostly decorative. Separately, market impact only exists for orders >50,000 shares, where price gaps by a hard-coded (qty/100000)*2.00 dollars and the whole book is wiped ("Black Swan"). Real microstructure impact is absent.

mock_engine.py · 109 LOC · LEGACY

An earlier, simpler engine that fabricates a Level-2 book from pure randomness and fakes fills as requested_qty × random(0.8,1.0). Fully superseded by true_engine.py; should be archived. Only value: a lightweight stub for UI testing.

2.2 · Swarm-Orchestration Layer

main.py · 40 LOC · CORE

The real entry point. Imports the AI/Torch stack first (a deliberate Windows DLL-ordering fix), instantiates 15 LiveMarketMaker + 4 LiveWhaleAgent + 80 LiveRetailAgent, hands them to a SwarmOrchestrator, runs the asyncio loop under the Windows selector policy. Clean and correct.

core/engine_client.py · 34 LOC · CORE

A thin, correct async wrapper around a single zmq.asyncio REQ socket exposing fetch_state() and send_order(). Fine as written — but it is the very object that forces the serialization of all 99 agents.

core/loop_manager.py · 57 LOC · CORE — SwarmOrchestrator

The perception→action loop. Each iteration it (1) enforces "dynamic participation" by randomly sleeping agents (30% awake when quiet, 100% on a news event), (2) liquidates & respawns any retail agent under $1,000, (3) fetches one state snapshot, (4) calls on_price_update() on every awake agent, (5) sends the resulting orders to the engine.

The "distributed" claim dies here. All 99 agents are iterated in a plain for loop and every order goes through one shared REQ socket, one synchronous round-trip at a time (await send → await recv). No parallelism, no multi-node fan-out, no per-agent socket. It's a fast sequential loop, not a swarm. The retail-liquidation logic here is also duplicated inside the engine, so the two can disagree about who is bankrupt.

run_mms.py run_whales.py run_retail.py · BROKEN / DEAD

Three near-identical scripts that spawn agents in isolated OS threads, each calling loop.run_until_complete(agent.run()). But none of the live agent classes define run() — they only expose on_price_update(). These crash with AttributeError the moment a thread starts. Remnants of an abandoned "one-thread-per-agent" architecture; delete or rebuild.

2.3 · AI & Agent Layer

agents/live_agents.py · 583 LOC · CORE ½ is dead comments

Loads the two PPO models + their VecNormalize stats at import time, plus the heuristic retail brain. ~200 lines are a commented-out duplicate of the same code — pure noise to delete. Defines the three live agent classes:

  • LiveWhaleAgent — genuinely uses its PPO model: maps the network's target-inventory % → desired position, clamps trade to ±10,000 shares, respects a 2 s cooldown, sends a MARKET order. The one place the AI actually drives behaviour.
  • LiveMarketMaker — loads & queries its PPO model but then ignores the model's bid/ask outputs and quotes spreads from random.uniform(0.001, 0.003); only the size dimension is loosely used. In the live path it's mostly a random-spread quoter.
  • LiveRetailAgent — calls the heuristic brain but then trades a random 1–20 shares regardless of the signal's conviction. Effectively a noise generator (arguably acceptable for a retail swarm — but it is not "AI").
Net effect. The headline "AI swarm of trained neural networks" is, at runtime, one model-driven agent type out of three. The trained intelligence largely does not reach the market.

agents/agents.py · 291 LOC · TRAIN — the most sophisticated code in the repo

Two Gymnasium environments used to train the PPO models offline:

  • SmartMoneyEnv (whale, 1-D action = target position %) — hysteresis dead-zone (separate ENTRY_THRESH=0.20 / EXIT_THRESH=0.05 so it doesn't churn), normalized reward, progressive drawdown penalty, inaction nudge, trend-carry bonus, 15% volume-participation cap, slippage/commission modelling, hard terminal drawdown stop at 30%.
  • MarketMakerEnv (3-D action = [bid offset, ask offset, quote size]) — explicitly eliminates look-ahead bias (quotes placed on the previous candle's close, filled against the current candle), enforces NSE tick-size rounding (the "phantom touch" fix), simulates queue position, penalizes inventory risk with a 3× "panic multiplier" when order-flow turns toxic.

These show real quant-engineering maturity. The irony: this rigour is spent on training, while the live path above discards much of it.

agents/core_environment.py · 74 LOC · TRAIN — base env

UniversalMarketEnv: loads a tick DataFrame, filters incomplete days, samples a random day per episode, exposes a scale-invariant 6-feature observation (VWAP distance, volatility, volume ratio, normalized RSI, OFI, portfolio return). current_step starts at 1 so the agent only ever sees the just-finished bar — clean anti-look-ahead.

⚠ Reads RSI_14 but the feature is never computed upstream → feature #3 is the constant 0.5 on every step. One of 6 inputs is dead.

agents/backtest_retail.py · 87 LOC · TRAIN

Defines HeuristicRetailSwarm — a rule-based brain (buy RSI<30, sell RSI>70, FOMO/panic on extreme order-flow, 10% pure noise) mimicking emotional retail with zero training. Its main() runs an offline backtest but reads data/processed_spy_1min.csv — a file not in the repo, so it can't run as shipped. (Note: models were trained on US SPY data, though the UI defaults to "TCS".)

agents/dummy_classes.py · 77 LOC · LEGACY — but conceptually important

Unused early agents (MarketMakerAgent, HedgeFundAgent, MomentumAgent). Crucially it contains HistoricalReplayer — an agent that walks a historical DataFrame and posts bracketing limit orders at each historical close. This is the embryonic seed of Pillar 1 (the history-repeater), but it is never instantiated or wired into the engine. The right idea, abandoned in a dead file.

agents/ml_models/*.zip + *.pkl · ARTIFACTS

Four binaries: PPO policies for MM & smart-money (~140 KB each — small MLP policies) + their VecNormalize statistics. They load successfully, but the training data is not in the repo, so the models cannot be reproduced or audited.

sanity_test.py · 55 LOC · UTIL

A smoke test that loads the normalizer + PPO model and runs a single inference to confirm the artifacts are intact. Useful — but it's a smoke test, not a unit test. There is no assertion suite anywhere in the project.

2.4 · Macro-Intelligence Layer

oracle.py · 155 LOC · WORKS — a real differentiator

Binds a REP socket on :5557, waits for a news headline from the UI, asks the engine which stock is active, prompts Gemini 2.5 Flash to infer the sector and return a strict JSON impact score in [-1, 1], converts that score into a precise share quantity, and fires a MARKET order to gap the price.

Tight coupling risk. The conversion required_qty = (target_gap/2.00)*100000 is a hand-derived inverse of the engine's hard-coded impact formula. The oracle and engine are joined by undocumented magic numbers (2.00, 100000, 50000); change one and the other silently miscalibrates. On any Gemini/JSON error it falls back to score 0.0 (safe, but silent — not the "robust fallback matrix" the README claims). It is also fully blocking — the whole oracle waits on each Gemini round-trip.

2.5 · Presentation Layer

bridge.py · 105 LOC · WORKS, with a concurrency bug

Serves dashboard.html; a background thread polls the engine at 1 Hz, reshapes state into an OHLC+book+tape+leaderboard payload, pushes it to the browser over SocketIO. Relays "start sim" and "inject news" to engine & oracle.

Two issues: (1) the same single REQ socket is shared by the poller thread and the SocketIO handlers — ZeroMQ REQ sockets aren't thread-safe and demand strict send/recv alternation; concurrent use can desync & hang the bridge. (2) OHLC high/low are fabricated with random.uniform jitter, not derived from real trades — the chart's wicks are cosmetic.

dashboard.html · 207 LOC · WORKS

A polished, single-file TradingView-style UI using lightweight-charts + socket.io: live candles + volume, a depth-shaded Level-2 book, a running trade tape, a PnL leaderboard, sector selector, and a "breaking news" injector. Correctly renders the engine's simulated UNIX clock. Minor: trade-tape row colors are assigned by Math.random() rather than by up/down tick.

The model-training defects (separate, equally important)

From the model-training report, the environment design is genuinely good (no look-ahead bias, chronological 80/20 split, scale-invariant obs, realistic microstructure, VecNormalize). But the training configuration has concrete defects that must be fixed before the numbers can be trusted:

#DefectConsequence & fix
M1BUG The RSI input is dead_get_obs() reads RSI_14 but prepare_data.py never computes it → feature #3 is constant 0.5 every step. The models effectively trained on 5 of 6 features. Fix: compute RSI_14 in feature engineering and retrain.
M2WEAK No best-model selection during trainingOnly a blind CheckpointCallback. The "final" 5M-step model is saved regardless of whether it's the best — RL routinely degrades late. Fix: carve a validation slice from TRAIN, use EvalCallback(best_model_save_path=…).
M3WEAK All hyper-parameters are stock defaultsent_coef=0 → premature convergence / under-exploration for the 3-D MM action; no LR schedule; no random seed (runs not reproducible). Fix: small entropy bonus (~0.001–0.01), LR schedule, fixed seed, light tuning.
M4MISMATCH Inconsistent reward scales between agentsWhale reward is a tiny fraction-of-capital (then VecNormalize divides again — double normalisation); MM reward is in raw dollars minus a λ=500 penalty. Completely different magnitudes, identical clip settings. Fix: unify reward engineering to a common normalized scale.
M5MISMATCH MM mis-wired in the live simsThe MM model (trained with a 3-D quoting action) is loaded into a SmartMoneyEnv wrapper (1-D action) just to reuse the obs/VecNormalize, and only action[0] (the bid-offset channel) is used as a "desired position." Semantically wrong. Fix: load the MM into MarketMakerEnv and use its real 3-D output.
M6SCOPE Single instrument, single regimeTrained only on SPY 2008–2021. 5M steps of repeated random-day sampling risks overfitting to that regime (incl. COVID). Generalisation to other tickers is unvalidated. Fix: multi-asset / multi-regime training set.
If you fix only one thing, fix R2. The entire commercial value rests on a single promise: the market reacts to the user. Today, random.gauss() on every state fetch swamps the contribution of real fills. Until the order book becomes the authoritative price source — mid/micro-price from best bid & ask, trades that genuinely walk and deplete depth, agents that re-quote in response — Chronos is a beautiful market animation, not a market simulation. Everything else is secondary.

04 What's Missing — Features Left After Phase 1

Phase 1 is a self-running simulation. To become a platform a customer can drive, these features are the bridge. The first two are the "two pillars" you correctly identified.

🏛️ Pillar 1 — The History-Repeater

Replay a real historical tape through the engine faithfully (the market behaves exactly as it did) up until the user's strategy executes its first trade. From that instant the tape is abandoned and the reactive twin takes over — agents and the book respond to the user's footprint, generating a counterfactual future that diverges from recorded history. This is the literal mechanism behind the §0 thesis.

Seed exists: HistoricalReplayer in dummy_classes.py. Needed: a "replay mode" in the engine that ingests real OHLC/L2 ticks, reconstructs a plausible book, detects the first user fill, and latches from deterministic-replay → reactive-simulation seamlessly (no price gap, carried inventory/RSI/regime, fixed RNG seed for auditability).

🚪 Pillar 2 — Strategy Script Runner

Let a user submit their own algorithm in any language (Python / C++ / Java / JS / R), register it as a first-class market participant, feed it the live state stream, and route its orders into the engine alongside the AI swarm. Without this there is no way for a customer to actually use Chronos.

Needed: the engine is already language-agnostic JSON-over-ZeroMQ, so the runner is a thin per-language SDK + a sandbox, not a new engine. Run each strategy in an isolated container (no network egress except the engine socket, CPU/mem/time limits, kill-switch). Normalize via an on_tick(state) → orders adapter. A single simulated clock must gate every participant so a fast language can't front-run a slow one.

5.2 · Wave 1 — Make the Simulation Honest (the keystone)

  • Mid-price = (best_bid + best_ask) / 2; better, micro-price = size-weighted mid (bid·ask_sz + ask·bid_sz)/(bid_sz+ask_sz).

Short answer: no — the current code is a prototype, not a minimal codebase. 12 Is Our Networking Like a Real Stock Market? Krishna

Short answer: no — and in two fundamental ways. (1) Real exchanges push market data to you; Chronos makes every agent pull it (REQ/REP "fetch state"). (2) Real exchanges run two separate network planes — a reliable TCP path for orders and a fast UDP-multicast path for data; Chronos shoves everything down one shared TCP socket, serialized. To be realistic, Phase 2 must adopt the real-world model. First, how real markets actually work.

12.1 · How a real stock exchange network works

┌────────────┐ ORDER ENTRY PLANE (reliability matters) ┌──────────────────┐ │ Participant│ ── FIX / binary (OUCH, iLink) over TCP ─────────▶ │ Exchange │ │ (broker / │ • per-session: logon, heartbeat, seq numbers │ GATEWAY tier │ │ HFT / fund)│ • guaranteed, ordered, exactly-once delivery │ (many sessions) │ └─────▲──────┘ └────────┬─────────┘ │ │ normalized msgs │ ┌────────▼─────────┐ │ MARKET DATA PLANE (speed + massive fan-out) │ SEQUENCER + │ │ ITCH / MDP 3.0 / Pillar over UDP MULTICAST (push) │ MATCHING CORE │ └──────────────◀─────────────────────────────────────────────── │ single thread / │ • one-to-many to thousands of subscribers │ symbol (Disruptor)│ • sequence numbers + A/B redundant feeds │ kernel-bypass, │ • TCP "recovery/snapshot" channel fills gaps │ colocated, ns │ └──────────────────┘
  • Order entry = TCP (often FIX, or a binary protocol like NASDAQ OUCH / CME iLink-SBE). You can never lose or reorder an order, so you need TCP's guaranteed, in-order, exactly-once delivery. Sessions have logon, heartbeats, sequence numbers, and resend/gap-fill.
  • Market data = UDP multicast (NASDAQ ITCH, CME MDP 3.0, NYSE Pillar, options OPRA). The exchange must fan one feed out to thousands of subscribers — TCP (one connection each) can't scale that, so it multicasts over UDP and pushes. A lost UDP packet is handled by sequence numbers (you detect the gap), A/B redundant feeds (two identical streams; you arbitrate), and a separate TCP retransmission/snapshot channel for recovery.
  • Sequencer / determinism — a single sequencer assigns a global total order to every event; the matching core is often single-threaded per symbol (the LMAX Disruptor ring-buffer pattern) for deterministic, replayable matching. Scale comes from sharding by symbol across many engines, not threading one engine.
  • Kernel bypass + colocation — to hit micro/nanosecond latency, exchanges & HFTs bypass the OS network stack (DPDK, Solarflare OpenOnload, RDMA/InfiniBand) and colocate servers in the exchange datacenter with equal-length cabling for fairness.
The one-line model: TCP for orders (can't drop one), UDP multicast push for data (must fan out to everyone, fast). Chronos does neither — it pulls everything over one TCP socket.

Note the one thing Phase 1 got right: a single-threaded matching core is actually how real exchanges achieve determinism. The mistake isn't the single thread — it's the pull-based single shared socket in front of it and the lack of a separate push data feed.

12.3 · The Phase-2 networking redesign (two planes)

PLANE A — ORDER ENTRY (reliable, TCP) agents / user strategies ──DEALER──▶ engine ROUTER :5555 • per-session socket identity (no more shared socket) • ack + sequence number per order • optional FIX gateway for institutions PLANE B — MARKET DATA (fast push, PUB/SUB) engine PUB :5556 ──broadcast──▶ ALL subscribers (agents, bridge, strategies) • every book delta + trade print + periodic L2 snapshot • sequence-numbered → subscribers detect gaps • ZeroMQ PUB over TCP for the product; epgm/UDP multicast "exchange realism mode" on LAN SEQUENCER (single thread): assigns monotonic seq to every event → deterministic + replayable (also powers Pillar-1 history-repeater)
  • Kills the pull serialization (R4) — agents subscribe to a pushed feed instead of each polling; orders go through a ROUTER that serves many DEALERs concurrently.
  • Matches real semantics — push data plane + reliable order plane + a sequencer, exactly like ITCH-over-UDP + FIX-over-TCP.
  • FIX gateway (simplefix / QuickFIX) gives institutions the protocol they already speak — ties straight into Pillar 2.
Honest caveat on UDP: true UDP multicast does not route over the public internet (multicast is a LAN/datacenter technology), so a cloud-hosted SaaS Chronos should push market data over ZeroMQ PUB/SUB on TCP (and WebSocket to browsers). Keep a UDP-multicast "exchange realism mode" for on-prem / colocation / LAN deployments and for authentically reproducing ITCH-style feeds with gap-recovery — that's the mode a serious HFT customer will want to test against. The architectural win is push + two planes + sequencer; the transport (TCP vs UDP) is a deployment switch.

14 Is Our Tech Stack Correct? All

Mostly yes — keep ~80% of it. Python stays (we know it, and it's correct for ML, orchestration & glue). 14.2 · Change — two real weak spots

⚠ Matching engine hot-loop → compiled core

A pure-Python dict-based book is fine for a demo but is the one place "Python everywhere" genuinely hurts — it's slow and nothing like a real venue. Path:

  • Now: drop in bmoscon/orderbook (a fast L2/L3 book in C, pip install order-book) — keeps Python ergonomics, removes the bottleneck.
  • Later: a Rust/C++ core with Python bindings (PyO3 / pybind11), or adopt NautilusTrader's Rust matching core. Python stays the control plane; the hot path is compiled.

⚠ Flask-SocketIO → FastAPI + Uvicorn

Flask-SocketIO in threading mode is what causes the thread-unsafe-socket bug (R7) and doesn't compose with the async engine. Move to FastAPI + Uvicorn (ASGI, async-native WebSockets). It speaks the same async language as the ZeroMQ asyncio client, so the bridge becomes one clean async path instead of a thread juggling a shared socket.
